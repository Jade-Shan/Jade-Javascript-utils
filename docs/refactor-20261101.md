# 拆分方案研究：应用、模块与 npm 包

研究日期：2026-11-01。本文是 [design-pkg.md](design-pkg.md)（npm 打包可行性）的后续，
回答两个问题：**混合了 TypeScript / Less / HTML 的本项目该不该拆**、**拆的话按什么边界拆**。

本文是研究文档，不是执行计划。其中「现状」部分的数据均来自实测（见[附录 A](#附录-a事实核对清单)），
「方案」部分是设计建议，未实施。

## 1. 结论先说

**不该按语言拆，该按产物角色拆。**

TypeScript、Less、HTML 在本项目里不是三个独立模块，而是同一个界面的三个面。
以窗口 UI 为例：[UIWindow.ts](../src/scripts/ts/ui/UIWindow.ts) 负责行为、
[desktop.less](../src/themes/window-ui/styles/desktop.less) 负责外观、
[test-jade-window-ui.html](../src/html/test-jade-window-ui.html) 负责挂载点，
三者描述的是同一个东西。按语言切开只会让一个功能的三块碎片散在三个地方，改一处要跨三个仓库。

真正需要切开的是**产物角色**：

| 角色 | 定义 | 当前状况 | 建议去处 |
|------|------|---------|---------|
| 库 | 任何项目 `import` 就能用的可复用代码 | 和应用代码混在 `src/scripts/ts/` 同一棵树里 | `packages/*`，各自发 npm 包 |
| 主题 | 可替换的视觉皮肤 | `comm.less` + `part.1.less` 变量模式，主题无法独立消费 | `packages/theme-*`，图片走 CDN |
| 应用 | 本站自己的页面和配置 | 散在 `blog/`、`html/`，部分写死进了库模块 | `apps/*`，不发包 |

按这三类切，TS / Less / HTML 会自然地聚到各自的包里，而不是被语言边界劈开。

### 2.3 三条并行的构建链

| 链路 | 入口 | 配置 | 输出 | 产物用途 |
|------|------|------|------|---------|
| CDN 构建 | [build.sh](../build.sh) → `npx gulp` | [tsconfig.json](../tsconfig.json) | `webroot/scripts/ts/` | nginx 静态资源，含 sourcemap 和 test 脚本 |
| npm 打包 | `npm run build:pkg` → `tsc` | [tsconfig.build.json](../tsconfig.build.json) | `dist/` | tarball，排除 `test*.ts` |
| HTML 模板 | `npx gulp include-html-dev` | [envs.js](../envs.sample.js) | `webroot/html/` | `gulp-file-include` 做 `@@` 变量替换 |

三条链共用一套源码树，互不冲突，但也意味着**改源码目录结构要同时改三处配置**。
另外 `envs.js` 在 `.gitignore` 里，而 [gulpfile.js:20](../gulpfile.js#L20) 顶层 `require("./envs")` ——
新克隆的仓库在 `cp envs.sample.js envs.js` 之前所有 gulp 任务都会挂。

### 2.4 两套主题系统，耦合方式不同

**内容主题（hobbit / lo-fi / paper-print）** 走 `comm.less` + `part.1.less` 变量模式：
[comm.less](../src/themes/comm.less) 467 行引用 86 个 Less 变量但自身不定义任何值，
各主题的 `part.1.less`（127 行）定义这些值。gulp 把两者 `concat` 成 `all.less` 再编译。

两个后果：

- `comm.less` 无法独立编译，必须配一套完整的变量表。作为 npm 包发布时它不是「可选依赖」而是「半成品」。
- gulp 的 `concat` 顺序是 `<theme>/styles/**/*.less` 在前、`comm.less` 在后。
  Less 变量是「最后一次赋值生效」，所以这个顺序下主题变量**反而会被 comm.less 里的赋值覆盖**
  —— 当前能跑是因为 `comm.less` 确实一个值都没定义。想给 `comm.less` 加默认值就必须先改这个顺序。

**window-ui 主题** 耦合方式完全不同。[UIWindow.ts](../src/scripts/ts/ui/UIWindow.ts) 往 DOM 上加 12 个 class，
而 [desktop.less](../src/themes/window-ui/styles/desktop.less) 只定义了其中一部分：

| class | 定义在哪 |
|-------|---------|
| `desktop`、`dock-bar`、`dock-content`、`cannot-select`、`title-bar-icon`、`title-bar-icon-text`、`title-bar-controls`、`menu-item`、`gap` | desktop.less |
| `window`、`window-body`、`title-bar`、`title-bar-text`、`inactive` | **98.css**（第三方包） |

也就是说 `window-ui` 这套 UI 对 `98.css` 有**隐式硬依赖**：不引 98.css，窗口就没有边框、标题栏和凹凸感。
而 98.css 当前只是 `devDependencies` 里的一项，且测试页面是从 `@@cdn3rd` 外链加载的，
`package.json` 里没有任何地方声明这层关系。拆包时这必须变成显式的 `peerDependencies`。

## 3. 拆分方案

### 3.1 为什么是 monorepo 而不是多仓库

本项目单人维护，一次改动经常同时碰到库和应用（比如给窗口加个按钮要改 `UIWindow.ts` + `desktop.less` + 测试页）。
多仓库会让这种改动变成「发版 → 升级依赖 → 再发版」的三步走。

建议用 **npm workspaces**（npm 10.9.7 原生支持，无需额外装 pnpm / lerna）：
一个仓库、一次 `npm install`、包之间用 workspace 协议互相引用，但各自有独立的 `package.json` 和版本号。

### 3.2 目标目录结构

```

├── package.json                  # workspaces 根，私有，不发布
├── tsconfig.base.json            # 共享编译选项
├── packages/                     # 可发布的库
│   ├── core/                     # basic + dataStructure          零 DOM
│   ├── geo2d/                    # ui/geo2d                       零 DOM

│   ├── canvas2d/                 # ui/canvas                      浏览器

│   ├── theme-core/              # comm.less 拆分后的结构层
```

### 3.3 包边界的取舍

16 个模块理论上能拆成 16 个包，也能合成 2 个。选 7 个库包（不含主题）的理由：

**按「有没有 DOM 依赖」切第一刀。** 这是 npm 消费方最在意的边界 ——
`core` 和 `geo2d` 零 DOM，在 Node / SSR / 单元测试里都能直接跑；
其余包 import 就需要浏览器环境。两档分开，使用方选包时不用读源码就知道能不能在 Node 里用。

**`geo2d` 单独成包。** 717 行纯几何运算（碰撞检测、最近点、射线求交），零 DOM、零业务假设，
是整个项目里复用价值最高的部分。合进 `core` 会让只想用几何库的人连带装上字符串工具和数据结构。

**`basic` + `dataStructure` 合成 `core`。** 两者都是零依赖的基础设施，合计 1378 行，
且 `web` / `geo2d` / `UIWindow` 都同时依赖它们。单独拆开只会多两个包名要记。

**`window-ui` 和 `sandtable` 各自成包。** 都超过 600 行、功能自成体系、互不依赖。
`window-ui` 还有 98.css 这层 peer 依赖要单独声明。

**`resource` 并入 `window-ui`。** 它存在的唯一目的是给 `UIWindow` 提供默认图标，没有独立使用场景。
但 310 行 base64 要按第 4.2 节改成可注入，不能原样搬。

依赖规则（上层可依赖下层，反向禁止）：

```
第 4 层  window-ui   sandtable   page-kit
第 3 层           canvas2d
第 2 层              web
第 1 层        core      geo2d
```

### 3.4 哪些不该发包

| 模块 | 理由 |
|------|------|
| `3rdLibTool` | 依赖 `$` / `MathJax` / `SyntaxHighlighter` / `showdown` **全局变量**。npm 消费方装的是真包（`import $ from 'jquery'`），这层包装会错位。建议留在 `packages/legacy-3rd` 但不发布，当作应用层的内部适配器，长期目标是删掉 |
| `blog/*` | 绑定本站后端 API，且含 CLAUDE.md 记录的两个待后端修复问题。属于应用 |
| `workout/*` | 业务数据（健身动作肌肉图），不是通用工具。若将来想复用，拆成 `muscle-svg`（渲染逻辑）+ 数据文件，见第 4.5 节 |
| `test*.ts` | 浏览器手动测试页脚本，归入对应的 `apps/*-demo` |

### 4.2 注入模式一：配置对象

**适用**：站点导航、主题列表、API 地址、品牌名。

库只定义类型，不定义值。值由应用在调用时传入。

```typescript
// packages/page-kit/src/types.ts —— 库：只有类型
export interface SiteConfig {
	brandName: string;
	brandLink: string;
	navItems: Array<NavTreeNode>;
	themes: Array<ThemeBinding>;
}

// apps/blog/src/site-config.ts —— 应用：值在这里
export const siteConfig: SiteConfig = {
	brandName: "Jade Dungeon",
	brandLink: "/",
	navItems: [ /* 原 SITE_NAV_ITEMS 内容 */ ],
	themes:   [ /* 原 SITE_THEMES 内容 */ ],
};
```

`SITE_NAV_ITEMS` / `SITE_THEMES` 从库的导出里删掉是 breaking change。
但它们目前只被 `blog/common.ts` 和 `blog/wiki.ts` 引用，都在本仓库内，影响可控。

`API_ROOT` 同理：`blog.ts` 和 `gallery.ts` 已经有 `basePath` 形参了，
只是没用 —— 把形参改成真正生效，并删掉 `common.ts` 里的 `API_ROOT` 常量，应用从 `envs.js` 或 URL 参数取值。

### 4.3 注入模式二：资源注册表

**适用**：base64 图标、桌面背景、占位图。

库提供注册接口和空的内置实现，应用自己塞资源。这样不用图标的消费方不会被迫下载 310 行 base64。

```typescript
// packages/window-ui/src/icon-provider.ts —— 库
export interface IconProvider {
	getIcon(name: string, size: IconSize): string | undefined;
}

let provider: IconProvider | undefined;
export function registerIconProvider(p: IconProvider): void { provider = p; }
export function getIcon(name: string, size: IconSize): string {
	// 没注册时退化成 CSS 占位，不内嵌任何图片数据
	return provider?.getIcon(name, size) ?? "";
}

// @jade-dungeon/window-ui-icons —— 可选的独立包，原 resource.ts 的 base64 搬到这里
```

拆成可选包而不是直接删：现有测试页面和 TRPG demo 都在用默认图标，
保留一个 opt-in 的包能让它们改一行 import 就继续跑。

### 4.4 注入模式三：选择器映射表

**适用**：`#widget-username` 这类「库代码写死了页面里必须有某个 id」的契约。

库不该假设页面长什么样。但也不必走到「每次调用传 7 个参数」的另一个极端 ——
把散落的选择器收进一张有默认值的表，应用想改就整表覆盖：

```typescript
// 库：默认值集中一处，且可覆盖
export interface UserWidgetSelectors {
	userName?: string; avatar?: string; avatarLink?: string;
	desc?: string; joinTime?: string; group?: string;
}
const DEFAULT_SELECTORS: Required<UserWidgetSelectors> = {
	userName: '#widget-username', avatar: '#widget-avatar',
	avatarLink: '#widget-avatar-lnk', desc: '#widget-user-desc',
	joinTime: '#widget-user-joined', group: '#widget-user-group',
};

static async loadUserInfo(apiRoot: string, userId: string,
	slt: UserWidgetSelectors = {}): Promise<void> {
	const s = { ...DEFAULT_SELECTORS, ...slt };
	// ...
}
```

这个模式项目里已经在用了 —— `webHtmlPage.ts` 的方法大多是
`elemSlt: string = "#topnav"` 这种带默认值的形参。差别只是 blog 层的选择器还没收拢。

### 4.5 注入模式四：数据与渲染分离

**适用**：workout 的 SVG 路径数据、文章卡片 HTML 模板。

`workout.ts` 512 行里约 363 行是数据。拆法：

```
packages/muscle-svg/        # 渲染逻辑：loadMuscleSvg、mergePathWithStyle，约 150 行
apps/workout/data/          # 数据：muscle-info.json、front-muscle.json、
                            #      back-muscle.json、pose-svg.json、workouts.json
```

数据改成 JSON 后有两个额外好处：一是运行时按需 `fetch`，首屏不用加载全部 SVG 路径；
二是数据能被非 TS 工具处理（比如直接用编辑器改路径、或写脚本从 SVG 文件生成）。

文章卡片模板（`common.ts:188-213`）同样是数据/逻辑混杂 —— 逻辑是「取文章、转 Markdown、填模板」，
Bootstrap 3 的栅格 class 是数据。改成渲染函数可注入：

```typescript
export type ArticleRenderer = (atc: UserArticle) => string;

static async loadArticleList(urlBuilder: (page: number) => string,
	currPage: number, render: ArticleRenderer = defaultBs3Renderer) { /* ... */ }
```

默认实现保留在应用层（`apps/blog`），库只定义类型。这样库对 Bootstrap 的绑定就断了。

## 5. CSS 的拆分

### 5.1 comm.less 改成「默认值 + 结构」两层

当前 `comm.less` 引用 86 个变量却不定义任何值，所以它不是一个能独立编译的单元。改法：

```
packages/theme-core/
├── variables.less      # 86 个变量全部给默认值
├── structure.less      # 原 comm.less 的结构规则
└── index.less          # @import "variables"; @import "structure";
```

主题包只覆盖自己关心的变量：

```less
// packages/theme-hobbit/index.less
@import "@jade-dungeon/theme-core/variables.less";   // 先拿默认值
@import "./overrides.less";                          // 再覆盖（原 part.1.less）
@import "@jade-dungeon/theme-core/structure.less";   // 最后应用结构
```

这里必须用显式 `@import` 替掉 gulp 的 `concat`。原因在 2.4 节：
当前 concat 顺序是主题文件在前、`comm.less` 在后，一旦 `comm.less` 开始定义默认值，
Less 的「最后赋值生效」规则会让默认值盖掉主题的覆盖值。显式 `@import` 把顺序写在文件里，不再依赖文件名排序。

改完的收益是主题从「必须提供全部 86 个变量」变成「只写想改的那几个」，新增主题的成本大幅下降。

### 5.2 图片路径参数化

主题 Less 里的图片引用是写死的相对路径（`url(../images/bg.jpg)`），
隐含假设「CSS 产物在 `themes/<name>/styles/`、图片在 `themes/<name>/images/`」。
换成 CDN 或别的目录布局就全断。加一个变量：

```less
// theme-core/variables.less
@asset-root: "../images";          // 默认保持现有相对路径，兼容当前构建

// 应用想换 CDN 时覆盖：
@asset-root: "//cdn.example.com/jadeutils.v3/themes/hobbit/images";
```

5.3 MB 图片仍留在 `assets/`，由 CDN 构建拷贝，不进任何 npm 包。
真要发包就单独发 `@jade-dungeon/theme-hobbit-assets`，让使用方自己决定装不装。

### 5.3 window-ui 的 98.css 依赖要显式化

2.4 节查明 `window`、`window-body`、`title-bar`、`title-bar-text`、`inactive`
这 5 个 class 由 98.css 提供，项目里没有任何地方声明这层关系。拆包时：

```json
// packages/window-ui/package.json
{
  "peerDependencies": { "98.css": "^0.1.21" },
  "peerDependenciesMeta": { "98.css": { "optional": true } }
}
```

标 `optional` 是因为 98.css 只影响外观不影响功能，不装也能跑（只是没有 Win98 质感）。
但这件事必须写进包的 README，否则使用方装完发现窗口没边框会以为是 bug。

### 5.4 UIWindow 的魔数与 CSS 对齐

`WIN_BORDER_SIZE = 6`、`WIN_BODY_PADDING = 25` 这些 TS 常量实际上在复述 CSS 里的尺寸。
两边各写一份，改一边忘另一边就会错位。两种处理：

- **保守**：保留 TS 常量，但在 `desktop.less` 对应规则上加注释指回 `UIWindow.ts` 的行号，至少让人改的时候能找到另一半。
- **彻底**：用 CSS 自定义属性做单一数据源，TS 侧 `getComputedStyle(el).getPropertyValue('--win-border-size')` 读取。

倾向保守方案。彻底方案要为 4 个数字引入运行时 DOM 读取和解析，收益不抵复杂度。

## 8. 风险

### 8.1 浏览器原生 ESM 解析不了包名（最需要先想清楚的一条）

项目当前靠 `<script type="module">` 直接加载编译产物，import 路径是 `./basic.js` 这种相对路径。
拆成多个包以后，包之间的 import 会变成 `@jade-dungeon/core` 这种裸模块名 —— **浏览器不会解析它**。

三个选项：

| 方案 | 做法 | 代价 |
|------|------|------|
| import maps | HTML 里声明 `<script type="importmap">` 把包名映射到 CDN 路径 | 现代浏览器原生支持，和 CDN 部署方式契合；需要在每个页面维护映射表 |
| 包间用相对路径 | 编译时把 `@jade-dungeon/core` 重写成 `../core/index.js` | 不引入新机制，但要加后处理步骤，且 npm 消费方和 CDN 消费方的产物不一致 |
| 引打包器 | Rollup / Vite | 和项目「无打包器」的既定原则冲突 |

倾向 **import maps**：它是浏览器原生能力，不需要构建步骤，且映射表可以由 `gulp-file-include` 从 `envs.js` 生成，
和现有的 `@@` 变量替换机制是同一套路子。这条需要在阶段 2 之前先做个最小验证。

### 8.2 breaking change 要攒在一起发

阶段 1 会删 `SITE_NAV_ITEMS`、`SITE_THEMES`、`API_ROOT` 等公开导出，
阶段 2 会改所有包名。按 semver 都是 major。当前版本 3.0.0，
建议所有 breaking change 攒到阶段 2 结束一次性发 4.0.0，中间不发版。

### 8.3 两个待后端修复的问题要原样保留

CLAUDE.md 明确记录：`recommands` 字段拼写、`pageCount + 1` 补偿。
重构时很容易顺手「修」掉这两处，会导致前端和后端不一致。
搬动 `blog/common.ts` 和 `blog/blog.ts` 时注意保留原注释。

### 8.4 没有自动化测试

这是贯穿所有阶段的风险。阶段 0 的单测只能覆盖 `core` / `geo2d`，
`UIWindow` / `sandtable` / blog 页面仍只能靠浏览器手动验证。
[design-pkg.md](design-pkg.md) 用过 jsdom 验证 `esp-unicode` 的行为等价性，
这个办法可以沿用：重构前后各跑一次，对比 DOM 输出。
