## 1. 结论先说

**不该按语言拆，该按产物角色拆。**

TypeScript、Less、HTML 在本项目里不是三个独立模块，而是同一个界面的三个面。
以窗口 UI 为例：[UIWindow.ts](../src/scripts/ts/ui/UIWindow.ts) 负责行为、
[desktop.less](../src/themes/window-ui/styles/desktop.less) 负责外观、
[test-jade-window-ui.html](../src/html/test-jade-window-ui.html) 负责挂载点，
三者描述的是同一个东西。按语言切开只会让一个功能的三块碎片散在三个地方，改一处要跨三个仓库。

真正需要切开的是**产物角色**：

| 角色 | 定义 | 当前状况 | 建议去处 |
|------|------|---------|---------|
| 库 | 任何项目 `import` 就能用的可复用代码 | 和应用代码混在 `src/scripts/ts/` 同一棵树里 | `packages/*`，各自发 npm 包 |
| 主题 | 可替换的视觉皮肤 | `comm.less` + `part.1.less` 变量模式，主题无法独立消费 | `packages/theme-*`，图片走 CDN |
| 应用 | 本站自己的页面和配置 | 散在 `blog/`、`html/`，部分写死进了库模块 | `apps/*`，不发包 |

按这三类切，TS / Less / HTML 会自然地聚到各自的包里，而不是被语言边界劈开。

### 2.3 三条并行的构建链

| 链路 | 入口 | 配置 | 输出 | 产物用途 |
|------|------|------|------|---------|
| CDN 构建 | [build.sh](../build.sh) → `npx gulp` | [tsconfig.json](../tsconfig.json) | `webroot/scripts/ts/` | nginx 静态资源，含 sourcemap 和 test 脚本 |
| npm 打包 | `npm run build:pkg` → `tsc` | [tsconfig.build.json](../tsconfig.build.json) | `dist/` | tarball，排除 `test*.ts` |
| HTML 模板 | `npx gulp include-html-dev` | [envs.js](../envs.sample.js) | `webroot/html/` | `gulp-file-include` 做 `@@` 变量替换 |

三条链共用一套源码树，互不冲突，但也意味着**改源码目录结构要同时改三处配置**。
另外 `envs.js` 在 `.gitignore` 里，而 [gulpfile.js:20](../gulpfile.js#L20) 顶层 `require("./envs")` ——
新克隆的仓库在 `cp envs.sample.js envs.js` 之前所有 gulp 任务都会挂。

### 2.4 两套主题系统，耦合方式不同

**内容主题（hobbit / lo-fi / paper-print）** 走 `comm.less` + `part.1.less` 变量模式：
[comm.less](../src/themes/comm.less) 467 行引用 86 个 Less 变量但自身不定义任何值，
各主题的 `part.1.less`（127 行）定义这些值。gulp 把两者 `concat` 成 `all.less` 再编译。

两个后果：

- `comm.less` 无法独立编译，必须配一套完整的变量表。作为 npm 包发布时它不是「可选依赖」而是「半成品」。
- gulp 的 `concat` 顺序是 `<theme>/styles/**/*.less` 在前、`comm.less` 在后。
  Less 变量是「最后一次赋值生效」，所以这个顺序下主题变量**反而会被 comm.less 里的赋值覆盖**
  —— 当前能跑是因为 `comm.less` 确实一个值都没定义。想给 `comm.less` 加默认值就必须先改这个顺序。

**window-ui 主题** 耦合方式完全不同。[UIWindow.ts](../src/scripts/ts/ui/UIWindow.ts) 往 DOM 上加 12 个 class，
而 [desktop.less](../src/themes/window-ui/styles/desktop.less) 只定义了其中一部分：

| class | 定义在哪 |
|-------|---------|
| `desktop`、`dock-bar`、`dock-content`、`cannot-select`、`title-bar-icon`、`title-bar-icon-text`、`title-bar-controls`、`menu-item`、`gap` | desktop.less |
| `window`、`window-body`、`title-bar`、`title-bar-text`、`inactive` | **98.css**（第三方包） |

也就是说 `window-ui` 这套 UI 对 `98.css` 有**隐式硬依赖**：不引 98.css，窗口就没有边框、标题栏和凹凸感。
而 98.css 当前只是 `devDependencies` 里的一项，且测试页面是从 `@@cdn3rd` 外链加载的，
`package.json` 里没有任何地方声明这层关系。拆包时这必须变成显式的 `peerDependencies`。

## 3. 拆分方案

### 3.1 为什么是 monorepo 而不是多仓库

本项目单人维护，一次改动经常同时碰到库和应用（比如给窗口加个按钮要改 `UIWindow.ts` + `desktop.less` + 测试页）。
多仓库会让这种改动变成「发版 → 升级依赖 → 再发版」的三步走。

建议用 **npm workspaces**（npm 10.9.7 原生支持，无需额外装 pnpm / lerna）：
一个仓库、一次 `npm install`、包之间用 workspace 协议互相引用，但各自有独立的 `package.json` 和版本号。

### 3.2 目标目录结构


### 3.3 包边界的取舍

16 个模块理论上能拆成 16 个包，也能合成 2 个。选 7 个库包（不含主题）的理由：

**按「有没有 DOM 依赖」切第一刀。** 这是 npm 消费方最在意的边界 ——
`core` 和 `geo2d` 零 DOM，在 Node / SSR / 单元测试里都能直接跑；
其余包 import 就需要浏览器环境。两档分开，使用方选包时不用读源码就知道能不能在 Node 里用。

**`geo2d` 单独成包。** 717 行纯几何运算（碰撞检测、最近点、射线求交），零 DOM、零业务假设，
是整个项目里复用价值最高的部分。合进 `core` 会让只想用几何库的人连带装上字符串工具和数据结构。

**`basic` + `dataStructure` 合成 `core`。** 两者都是零依赖的基础设施，合计 1378 行，
且 `web` / `geo2d` / `UIWindow` 都同时依赖它们。单独拆开只会多两个包名要记。

**`window-ui` 和 `sandtable` 各自成包。** 都超过 600 行、功能自成体系、互不依赖。
`window-ui` 还有 98.css 这层 peer 依赖要单独声明。

**`resource` 并入 `window-ui`。** 它存在的唯一目的是给 `UIWindow` 提供默认图标，没有独立使用场景。
但 310 行 base64 要按第 4.2 节改成可注入，不能原样搬。

依赖规则（上层可依赖下层，反向禁止）：

```
第 4 层  window-ui   sandtable   page-kit
第 3 层           canvas2d
第 2 层              web
第 1 层        core      geo2d
```

**适用**：站点导航、主题列表、API 地址、品牌名。

### 4.3 注入模式二：资源注册表

**适用**：base64 图标、桌面背景、占位图。

库提供注册接口和空的内置实现，应用自己塞资源。这样不用图标的消费方不会被迫下载 310 行 base64。

```typescript
// packages/window-ui/src/icon-provider.ts —— 库
export interface IconProvider {
	getIcon(name: string, size: IconSize): string | undefined;
}

let provider: IconProvider | undefined;
export function registerIconProvider(p: IconProvider): void { provider = p; }
export function getIcon(name: string, size: IconSize): string {
	// 没注册时退化成 CSS 占位，不内嵌任何图片数据
	return provider?.getIcon(name, size) ?? "";
}

// @jade-dungeon/window-ui-icons —— 可选的独立包，原 resource.ts 的 base64 搬到这里
```

拆成可选包而不是直接删：现有测试页面和 TRPG demo 都在用默认图标，
保留一个 opt-in 的包能让它们改一行 import 就继续跑。

### 4.5 注入模式四：数据与渲染分离

**适用**：workout 的 SVG 路径数据、文章卡片 HTML 模板。

`workout.ts` 512 行里约 363 行是数据。拆法：


## 5. CSS 的拆分

### 5.1 comm.less 改成「默认值 + 结构」两层

当前 `comm.less` 引用 86 个变量却不定义任何值，所以它不是一个能独立编译的单元。改法：

```
packages/theme-core/
├── variables.less      # 86 个变量全部给默认值
├── structure.less      # 原 comm.less 的结构规则
└── index.less          # @import "variables"; @import "structure";
```

主题包只覆盖自己关心的变量：

```less
// packages/theme-hobbit/index.less
@import "@jade-dungeon/theme-core/variables.less";   // 先拿默认值
@import "./overrides.less";                          // 再覆盖（原 part.1.less）
@import "@jade-dungeon/theme-core/structure.less";   // 最后应用结构
```

这里必须用显式 `@import` 替掉 gulp 的 `concat`。原因在 2.4 节：
当前 concat 顺序是主题文件在前、`comm.less` 在后，一旦 `comm.less` 开始定义默认值，
Less 的「最后赋值生效」规则会让默认值盖掉主题的覆盖值。显式 `@import` 把顺序写在文件里，不再依赖文件名排序。

改完的收益是主题从「必须提供全部 86 个变量」变成「只写想改的那几个」，新增主题的成本大幅下降。

### 5.2 图片路径参数化

主题 Less 里的图片引用是写死的相对路径（`url(../images/bg.jpg)`），
隐含假设「CSS 产物在 `themes/<name>/styles/`、图片在 `themes/<name>/images/`」。
换成 CDN 或别的目录布局就全断。加一个变量：

```less
// theme-core/variables.less
@asset-root: "../images";          // 默认保持现有相对路径，兼容当前构建

// 应用想换 CDN 时覆盖：
@asset-root: "//cdn.example.com/jadeutils.v3/themes/blog/hobbit/images";
```

5.3 MB 图片仍留在 `assets/`，由 CDN 构建拷贝，不进任何 npm 包。
真要发包就单独发 `@jade-dungeon/theme-hobbit-assets`，让使用方自己决定装不装。

### 5.3 window-ui 的 98.css 依赖要显式化

2.4 节查明 `window`、`window-body`、`title-bar`、`title-bar-text`、`inactive`
这 5 个 class 由 98.css 提供，项目里没有任何地方声明这层关系。拆包时：

```json
// packages/window-ui/package.json
{
  "peerDependencies": { "98.css": "^0.1.21" },
  "peerDependenciesMeta": { "98.css": { "optional": true } }
}
```

标 `optional` 是因为 98.css 只影响外观不影响功能，不装也能跑（只是没有 Win98 质感）。
但这件事必须写进包的 README，否则使用方装完发现窗口没边框会以为是 bug。

### 5.4 UIWindow 的魔数与 CSS 对齐

`WIN_BORDER_SIZE = 6`、`WIN_BODY_PADDING = 25` 这些 TS 常量实际上在复述 CSS 里的尺寸。
两边各写一份，改一边忘另一边就会错位。两种处理：

- **保守**：保留 TS 常量，但在 `desktop.less` 对应规则上加注释指回 `UIWindow.ts` 的行号，至少让人改的时候能找到另一半。
- **彻底**：用 CSS 自定义属性做单一数据源，TS 侧 `getComputedStyle(el).getPropertyValue('--win-border-size')` 读取。

倾向保守方案。彻底方案要为 4 个数字引入运行时 DOM 读取和解析，收益不抵复杂度。

## 9. import maps 的落地实现

实施日期：2026-11-01。这一节记录已经改进代码库的内容，不是设计建议。

### 9.1 最小验证：嵌套层的裸模块名能不能解析

拆包后的关键场景不是「页面顶层用裸模块名」，而是**被加载的模块自己也用裸模块名 import 别的包**。
先用一个三层 POC 验证（`/tmp` 下，不入仓库）：页面以裸模块名加载 `probe-mid.js`，
而 `probe-mid.js` 自己 `import '@poc/leaf'` 和 `import '@poc/sub/probe-prefix.js'`。

headless Edge 实测输出 `mid-ok + leaf-ok + prefix-ok`，三件事都成立：

- 页面顶层的裸模块名可解析
- **嵌套模块里的裸模块名同样可解析**（import map 作用于整张模块图，不只是入口）
- 带尾斜杠的前缀映射可用

第二条是拆包的前提，这条成立之后方案才算可行。

### 9.2 映射表从 package.json 的 exports 派生

映射表不手写第二份清单，由 [gulpfile.js](../gulpfile.js) 的 `buildImportMap()`
读 `package.json` 的 `exports` 生成，把 `./dist/` 前缀换成 `envs.js` 里的 `importMapRoot`：

```javascript
// exports 里的 "./basic": { "default": "./dist/basic.js" }
// 生成 "@jade-dungeon/jade-utils/basic": "../scripts/ts/basic.js"
```

这样做的收益是**页面里的 import 路径和 npm 消费方完全一致**：

```javascript
// CDN 页面里                                    npm 项目里
import { WebUtil } from '@jade-dungeon/jade-utils/web';   // 两边一字不差
```

末尾额外加一条带尾斜杠的前缀键 `"@jade-dungeon/jade-utils/": "../scripts/ts/"`，
兜住 `exports` 里没列的模块（`test*.js` 等）。import map 的解析规则是精确键优先于前缀键，
所以两者共存不冲突。

生成结果共 18 条（17 条 exports 别名 + 1 条前缀兜底）。

### 9.3 注入方式

`gulp-file-include` 对 context 变量是原样插入、不转义引号（已实测），
所以 JSON 可以直接塞进 context，不需要多一个构建产物：

- `initCurrEnv()` 里 `env.importmap = JSON.stringify({imports: buildImportMap(env)}, null, 1)`
- 新增 [parts/importmap.html](../src/html/parts/importmap.html) 只做一件事：输出 `<script type="importmap">@@importmap</script>`
- 10 个有模块 import 的页面各 include 一次这个 partial

两个硬约束写在 partial 的注释里：必须在第一个 `<script type="module">` 之前，且一个文档只能有一个 import map。
`index.html` 和 `test-dock.html` 没有模块 import，不含 import map。

### 9.4 顺带修掉的一个既存 bug

实施过程中发现：构建产物 `webroot/html/blog.html` 里的 import 路径是 `./scripts/ts/web.js`，
而页面在 `webroot/html/` 下、脚本在 `webroot/scripts/ts/` 下 —— `webroot/html/scripts/` 并不存在，
这个相对路径指向空处。根因是 `envs.js` 的 `staticRoot: "."` 对这个输出布局不成立，应为 `..`。

新增的 `importMapRoot` 配置项把模块基址收到了一处，顺带修正了这个路径。
换 CDN 时只改这一个值，填绝对地址即可。

当时 `staticRoot` 本身没有动，只提了一句「那部分是否同样有问题没有核查」。
**后来核查了，确实有同样的问题** —— 而且比预想的更严重：页面服务在 8082、
静态资源在 8081，`staticRoot: "."` 不管填 `.` 还是 `..` 都拼不出来，
必须填绝对地址。详见 [11.4](#114-envsjs-的键有增有减) 与 [11.5](#115-dev-配置的逐项核对)。

## 10. API_ROOT 的清理

实施日期：2026-11-01。这一节记录已经改进代码库的内容。

### 10.1 问题是怎么暴露的

第 9 节的 import map 装好之后，`blog.html` 在浏览器里报：

```
已拦截跨源请求：同源策略禁止读取位于
http://www.jade-dungeon.cn:8088/api/blog/loadUserById?userId=u001 的远程资源
```

**这个错误不是 import maps 引入的，是它让一个一直存在的问题显形了。**
在 9.4 节修掉路径 bug 之前，`blog.html` 的模块路径指向不存在的位置，
脚本 404 → `BlogPage.initBlogPage()` 从未执行 → API 请求根本没发出去。
路径修好后模块真的跑起来，写死的生产域名才开始发请求。

这类「修好 A 之后 B 的错误才出现」的情况，说明 B 本来就坏着，只是被 A 盖住了。

**但这条报错信息本身的直接原因是后端服务当时没活着**，不是写死的域名。
写死域名的问题是「dev 环境该打 dev 后端却打了生产」，这是配置问题，
与 CORS 报错是两件事 —— 哪怕生产后端活着且 CORS 头正常，写死域名也一样该改。
后端挂掉为什么会报成 CORS，见 [10.6 节](#106-排查-cors-报错时先确认后端活着)。

### 10.2 根因

`common.ts` 写死 `API_ROOT = "//www.jade-dungeon.cn:8088/"`，
而 `blog.ts` / `gallery.ts` 的 `initBlogPage(basePath, ...)` 收了 `basePath` 形参，
进函数第一件事就是 `let apiRoot = API_ROOT;` 把它覆盖掉。
页面侧传的是空串，传什么都没用 —— 就是 4.1 节记的「参数形同虚设」。

### 10.3 改法

按 4.2 节的配置对象模式，让已有的形参真正生效：

- 删掉 `common.ts` 的 `API_ROOT` 常量
- 新增 `normalizeApiRoot(apiRoot)`：补齐尾斜杠，空值退化为同源根路径 `/`。
  调用处用 `${apiRoot}api/blog/xxx` 拼接，所以根路径必须带 `/` 结尾，
  而 `envs.js` 的 `apiRoot` 是不带的（`//localhost:8082`），需要规整
- `blog.ts` / `gallery.ts` 改为 `let apiRoot = normalizeApiRoot(basePath);`
- `blog.html` / `gallery.html` 把 `''` 改成 `'@@apiRoot'`，由 `envs.js` 供值

改完 API 地址就跟着环境走：dev 打 `//localhost:8082`，rls 打配置里的地址。

### 10.4 验证

用 mock 后端（`/tmp` 下的 python 脚本，带 `Access-Control-Allow-Origin: *`，不入仓库）
在 8082 起服务，headless Edge 跑 `blog.html`：

| 验证项 | 结果 |
|--------|------|
| `tsc --noEmit` 全量类型检查 | ✅ 0 错误 |
| 源码里残留 `API_ROOT` | ✅ 0 处 |
| 产物里的调用参数 | ✅ `initBlogPage('//localhost:8082', ...)` |
| 产物里不再出现生产 API 域名 | ✅ 仅剩 `parts/footer.html` 的页脚文字 |
| 用户信息渲染 | ✅ `MockUser` 出现 |
| 文章列表渲染 | ✅ `MockArticle` 出现 |
| 推荐列表渲染 | ✅ `MockRecommend` 出现 |

三个接口的数据都渲染出来了，说明整条链路通了。

### 10.5 没有一并处理的

- **`userId = "teo"` 默认值仍在** —— 4.1 节记的另一条，不影响本次报错，至今未动
- ~~测试脚本里的生产 URL 仍在~~ —— 已在[第 11 节](#11-demo-环境配置注入与跨源判定修正)处理。

  本次改的是「别再打生产域名」，至于目标端口上有没有服务，属于后端侧的事

### 10.6 排查 CORS 报错时先确认后端活着

**后端服务挂掉时，浏览器报的也是 CORS 错误。** 这条是实际踩出来的：
后端进程崩了之后页面报 CORS，重启后端错误就消失了，而后端的 CORS 配置一直没动过。

原因是跨源请求失败时，浏览器拿不到带 `Access-Control-Allow-Origin` 的响应 ——
服务没响应和服务响应了但没这个头，在浏览器看来都是「跨源检查没通过」。
Firefox 对连不上的情况报的就是「CORS 请求未能成功」，且**状态码显示 `(null)`**。

实测过 XHR 层面的表现（与项目 `doHttp()` 的实现一致）：

| 情况 | JS 收到 | 服务端是否收到请求 |
|------|---------|------------------|
| 服务活着 + 有 CORS 头 | `onload`，`status=200` | 是 |
| 服务活着 + 无 CORS 头 | `onerror`，`status=0` | **是** |
| 端口上没有服务 | `onerror`，`status=0` | 否（无服务） |

后两种在 JS 里完全一样，都是 `onerror` + `status=0`，光看代码分不出来。

**所以排查顺序应该是先确认后端活着，再查 CORS 配置**：

```bash
# 1. 后端端口有没有服务（000 = 连不上，此时「CORS 错误」是假象）
curl -s -o /dev/null -w "%{http_code}\n" --max-time 3 http://localhost:8082/

# 2. 确认活着之后，再看响不响 CORS 头
curl -s -D - -o /dev/null http://localhost:8082/api/blog/loadUserById?userId=u001 \
  | grep -i access-control
```

两个判断依据：

- **状态码 `(null)` 或 `status=0` 且后端日志里没有这条请求** → 后端没活着，先重启后端
- **后端日志里有这条请求** → 请求到了，是真的缺 CORS 头，才去查后端配置

本项目后端的 CORS 配置已确认没问题，所以遇到 CORS 报错时**优先怀疑后端进程崩了**。

## 11. demo 环境配置注入与跨源判定修正

实施日期：2026-11-01。详细的调查过程与决策依据见

### 11.1 demo 脚本的地址改为注入

调查发现写死的请求地址共 11 处，**全部在 demo / 测试脚本里**
（业务代码的最后一处 `API_ROOT` 已在第 10 节清掉）。涉及两个端口：

| 端口 | 用途 | 来源键 |
|------|------|--------|
| `:8088` | 后端 API（含图片代理接口） | `apiRoot` |
| `:8081` | CDN 静态资源 | `staticRoot` / `cdn3rd` |

做法按 [4.2 节](#42-注入模式一配置对象)的配置对象模式：

- 新建 `src/scripts/ts/env.demo.ts`，定义 `DemoEnvConfig`（`apiRoot` / `themeRoot` / `cdn3rd`）
  和取值函数 `demoEnv()`。**不进 `package.json` 的 `exports`** —— demo 专用，不对外发布
- `testJadeUtils.ts` 4 个函数、`testJadeTRPG.ts` 2 个入口加 `env?: DemoEnvConfig` 形参。
  写死的地址不在入口函数里，形参要继续往内层传
- 5 个 demo 页面在调用处注入 `@@apiRoot` / `@@staticRoot/themes` / `@@cdn3rd`
- 缺值时 `demoEnv()` 返回空串，**不兜底成生产地址** —— 兜底会让「页面忘了传参」
  静默变成「偷偷去打生产环境」

`DemoEnvConfig.themeRoot` 在 `envs.js` 里没有同名键：它就是 `staticRoot` 加 `/themes`，
页面侧拼出来传进去，不另设配置项。

两处刻意保留：

| 位置 | 保留理由 |
|------|---------|
| `testSceneData` 里两行图片 URL | 改造后端时要作为对比样本，明文比对方便 |
| `testJadeUtils.ts` 的图床图片 `s21.ax1x.com` | 测试图片代理的夹具，换成本站图片就测不到代理了 |

### 11.2 跨源判定改用 origin 比对

改完地址注入后发现 TRPG demo 的图片不走代理了。根因在
[web.ts](../src/scripts/ts/web.ts) 原来的判定条件：

```typescript
if (cfg?.proxyUrl && url.indexOf('http') == 0) {   // 只认 http 开头
```

代理的目的是绕开跨源图片对 canvas 的污染，所以判定标准该是「是否跨源」，
而不是「URL 长什么样」。原条件漏掉协议相对的 `//host/path`，
又会把同源的 `http://自己站/x.jpg` 也送进代理（没必要）。

改为 `new URL(url, location.href)` 解析后比对 origin，并把**绝对地址**传给代理

| 跨源协议相对 `//other:8081/x.jpg` | DIRECT（**bug**） | PROXY |
| 跨源绝对 `http://other:8081/x.jpg` | PROXY | PROXY |
| `data:` URI | DIRECT | DIRECT |

### 12.1 选型：Node 内置 `node:test`，不装框架

| 方案 | 取舍 |
|------|------|
| **`node:test`（已采用）** | Node 20+ 内置，零新增依赖。缺点是没有 `expect` 风格的断言和快照 |
| vitest | 生态好、体验佳，但会带进 Vite 及其依赖树，与项目「无打包器」的既定原则冲突 |
| jest | 需要额外配 ESM 支持，本项目是纯 ESM，配置成本高 |

只新增了一个 devDependency：`@types/node`（给 `node:test` / `node:assert` 提供类型）。
项目本来就有 `@types/jquery`，不算破例。

### 12.2 测的是编译产物，不是源码

```
tsconfig.test.json  →  把 src/ 和 test/ 一起编到 .test-build/  →  node --test 跑产物
```

这样测的东西和 npm 消费方拿到的是同一种，而不是「源码在 ts-node 里的表现」。
[design-pkg.md](design-pkg.md) 已经验证过编译产物在 Node 下可直接 import，
这里是顺着同一条路。

三份 tsconfig 的分工变成：

| 配置 | 用途 | 输出 |
|------|------|------|
| `tsconfig.json` | gulp 的 CDN 构建 | `webroot/scripts/ts/`，含 `test*.ts` 和 sourcemap |
| `tsconfig.build.json` | npm 打包 | `dist/`，排除 `test*.ts` |
| `tsconfig.test.json` | 单元测试 | `.test-build/`，含 `src/` 和 `test/` |

一个容易踩的点：根 `package.json` 没有 `"type": "module"`，所以 Node 会把
`.test-build/` 里的 ESM 产物当 CJS 解析并报 `Cannot find module`。
解决办法和 `build:pkg` 对 `dist/` 做的一样 —— 往输出目录写一个
`{"type":"module"}` 的 `package.json`，由 `build:test` 脚本自动完成。

#### 为什么不把三份 tsconfig 合成一份

评估过，结论是**不合并**。两个硬障碍，第一个是决定性的：

**Node 类型是编译单元级的，不是文件级的。** 测试需要 `types: ["node"]`，
浏览器代码不该有。实测对照：

| 写法 | `types: []`（现状） | `types: ["node"]`（合并后） |
|------|------------------|------------------------|
| 浏览器代码里 `process.env.HOME` | **报错 TS2591 挡住** | 放过去了 |
| `const t: number = setTimeout(...)` | 正常 | **报错** —— Node 的 `setTimeout` 返回 `Timeout` 不是 `number` |

试过用三斜线指令 `/// <reference types="node" />` 只在测试文件里引入 ——
**不行**，它影响整个编译单元。同一份浏览器代码单独编译时 `process` 被挡住，
和带三斜线的测试文件一起编译时就放过去了。

第二行那条反向问题也要注意：合并会给浏览器代码**引入新的编译错误**。
项目里 7 处 `setTimeout` 恰好都没接返回值，所以今天不会炸，但这是埋着的坑。

**第二个障碍：`rootDir` 不同导致产物结构变化。** 测试要同时编 `src/` 和 `test/`
两棵树，所以 `rootDir` 必须是 `.`；而 CDN 构建用 `src/scripts/ts`，产物直接落在
`outDir` 根下。合并后会变成 `webroot/scripts/ts/src/scripts/ts/basic.js`，
import map 的 `importMapRoot` 和 `package.json` 的 17 条 `exports` 路径全得跟着改。

几种合并方案的代价：

| 方案 | 结果 |
|------|------|
| 单份 + `rootDir: "."` | 两个障碍都踩 |
| 测试文件挪进 `src/scripts/ts/` | `rootDir` 解决了，但 CDN 要排除测试、测试要包含测试，`include`/`exclude` 还是两套，文件数没减 |
| 测试改跑 `dist/`、写成纯 `.js` | 能减到 2 份。代价是测试代码失去类型检查，且 `npm test` 要依赖 `build:pkg` 先跑 |
| project references（`composite`） | 能保持编译单元隔离，但配置更多不是更少 |

`tsconfig.test.json` 去掉注释只有 12 行有效内容，且全是 `extends` 之后的差异项。
用 12 行换「浏览器代码不会误用 Node API」这个编译期保证，划算。

## 13. checkPointLineSide 与 revolveRay 的修复

实施日期：2026-11-01。这是写单元测试时顺带挖出来的，不在原计划内。

### 13.1 原实现的四个 bug

`checkPointLineSide` 原来按点的 y 落在哪个区间分三个分支算：

```typescript
let ll = line.b.y < line.a.y ? { a: line.b, b: line.a } : line;
let angleAB = Math.atan2(ll.b.y - ll.a.y, ll.b.x - ll.a.x);
if (ll.a.y < p.y && p.y < ll.b.y) {           // 分支 1
	let angleAP = Math.atan2(p.y - ll.a.y, p.x - ll.a.x);
	side = angleAB - angleAP;
} else if (p.y < ll.a.y) {                     // 分支 2
	let cx = ll.a.x - ((ll.b.x - ll.a.x) / (ll.b.y - ll.a.y) * (ll.a.y - p.y))
	side = p.x - cx;
} else if (ll.b.y < p.y) {                     // 分支 3
	let cx = (ll.b.x - ll.a.x) / (ll.b.y - ll.a.y) * (p.y - ll.a.y) - ll.a.x;
	side = p.x - cx;
}
```

| # | bug | 触发条件 |
|---|-----|---------|
| 1 | 分母 `ll.b.y - ll.a.y` 为 0，返回 ±Infinity | 水平线（`a.y === b.y`） |
| 2 | 三个分支条件都是开区间，全部落空，`side` 保持初值 `0`，等于谎报「点在线上」 | `p.y` 正好等于某个端点的 y |
| 3 | 分支 3 的截距项写成 `- ll.a.x`，应为 `+ ll.a.x` | `a.x !== 0`。`a.x === 0` 时碰巧看不出来 |
| 4 | 分支 1 返回角度差，分支 2/3 返回横向距离，量纲不一致 | 总是如此，只有符号可用 |

bug 3 的核对：线 `a=(5,0) b=(15,10)`、点 `(10,20)`，
分支 3 算出 `cx = 15`，正确值是 `a.x + (b.x-a.x)/(b.y-a.y) * (p.y-a.y) = 25`。

全量扫描（线段端点和点各在 7×7 / 9×9 网格上取值，共 190512 组）的结果：
**43212 组符号错误、21168 组返回非有限值**。不是边角问题。

### 13.2 `revolveRay` 根本不需要这个函数

`checkPointLineSide` 在 `src/` 里的唯一调用方是 `revolveRay`，
用来处理「跨三个象限」的情形。而 `revolveRay` 的 `diff` 字段是给
`CanvasUtils.drawFanByRays()` 用的：

```typescript
cvsCtx.arc(..., revole.start, revole.end, revole.diff < 0);
```

`diff` 的符号决定 `arc()` 的 `anticlockwise` 参数，大小决定扇形张角。
所以它要的就是**短弧的有向角** —— 两条射线之间不超过半圈的那个转法。

这是个一行就能算的标准操作：`atan2` 的值域是 `(-π, π]`，两者相减落在
`(-2π, 2π)`，归一化回 `(-π, π]` 即可。原来那套按象限分支 + 侧向判断
是绕了远路，而且绕错了。

实测对照（圆周取 72 个点两两组合，共 5112 组）：

| 圆心 | 与「短弧归一化」一致 | 不一致 |
|------|------------------|-------|
| `(37, -19)` | 5112 | **0** |
| `(0, 0)` | 5083 | 29（全是正对 180°，且原实现在这里给的符号本身不稳定） |

正对 180° 时两条弧都是半圈，符号在数学上任意。原实现时而 `+180°` 时而 `-180°`，
没有需要保留的既定约定，所以新实现用标准区间 `(-π, π]`。

### 13.3 改法

**`revolveRay`**：删掉象限分支和侧向判断，改为直接归一化。
顺带去掉了对 `checkPointLineSide` 的依赖。

**`checkPointLineSide`**：它是公开导出，外部可能有调用方，所以修而不删。
改用叉积表达同一个谓词：

```typescript
// 方向归一化：y 小的在前；y 相同时 x 小的在前
let ll = line;
if (line.b.y < line.a.y || (line.b.y === line.a.y && line.b.x < line.a.x)) {
	ll = { a: line.b, b: line.a };
}
return (ll.b.y - ll.a.y) * (p.x - ll.a.x) - (ll.b.x - ll.a.x) * (p.y - ll.a.y) + 0;
```

四个 bug 一次解决：没有除法（bug 1）、没有分支（bug 2、4）、没有手写截距（bug 3）。

两个细节：

- **方向归一化保留了**。它让函数对 `a`/`b` 的书写顺序不敏感，语义是
  「相对自下而上方向的侧」。这是原实现有意的设计，不是 bug ——
  和裸叉积（符号随 a→b 方向翻转）的区别就在这里。
  水平线的方向取为从左到右，补上了原实现没定义的情形
- **末尾 `+ 0` 是把 `-0` 归一成 `+0`**。共线时某一项会算出 `0 * 负数 = -0`，
  使整个表达式得到 `-0`。虽然 `-0 === 0` 成立，但 `Object.is` 和严格断言会区分，
  容易让调用方的「是否在线上」判断踩坑

### 13.6 删掉两个零引用的函数

查调用关系时发现 `pointToLine()` / `pointToLineDistance()` 是一对闭环的死代码：

| 函数 | 内部调用方 |
|------|-----------|
| `pointToLineDistance` | 零 |
| `pointToLine` | 仅被 `pointToLineDistance` 调用 |

两者还带着一处不一致：`pointToLine` 对轴对齐线段（`a.x === b.x` 或
`a.y === b.y`）的两个提前返回分支没做投影参数的 `[0, 1]` 夹取，斜线分支却做了。
所以同一个函数对不同输入分别在算「点到直线」和「点到线段」：

```
垂直线段 (0,0)-(0,10)，点 (5,100)    -> 垂足 y=100（未夹取，落在线段外）
斜线段   (0,0)-(10,10)，点 (100,100) -> 垂足 (10,10)（夹到端点）
```

与其修一个没人用的函数，不如删掉 —— 需要点到直线的距离时，
用 `|cross| / |d|` 一行就能算（见 [geo.md](geo.md) 的叉积一节），
还不用担心夹取语义。

删除后的处理：

- `geo2d.utils.test.ts` 里针对这两个函数的 5 条测试删掉
- 其中测叉积与距离关系的那条保留，改为自己算点到直线的距离，不再依赖被删的函数
- `geo.md` 里相关段落改写，并新增一条经验「零引用的函数直接删」

### 13.7 formatAngle 的归一化修复

`IAngle` 接口的注释本来就写明 `fmtAgl: 规范化弧度 [0, 2π)`、
`fmtDgr: 规范化度数 [0, 360)`，所以这是实现没兑现自己声明的契约。

原实现 `angle < 0 ? PI_DOUBLE + angle : angle` 只补一次 2π，
所以 `-3π` 补完仍为负、`3π` 也没折回区间内。改用取模：

```typescript
let fmtAgl = angle % Geo2DUtils.PI_DOUBLE;
if (fmtAgl < 0) { fmtAgl = fmtAgl + Geo2DUtils.PI_DOUBLE; }
fmtAgl = fmtAgl + 0;
```

`+ 0` 的理由和 `checkPointLineSide` 一样：`-0 % 2π` 与 `-2π % 2π` 都得到 `-0`，
而 `-0 < 0` 为假，不会进入「加一圈」的分支。

验证：扫描 984 个角度（±20 圈 × 24 个方位），越界零例、`-0` 零例、
与输入不差整数圈零例。

**顺带记录一个固有限制**：`2π` 是无理数的浮点近似，圈数很大时取模会留下残差 ——
`formatAngle(100π).fmtAgl ≈ 8.14e-13`，数学上应为 0。这是浮点取模的固有误差，
换任何写法都躲不开。已写进 JSDoc 和 geo.md：**比较角度要用容差，不要用 `===`**。
我自己写断言时先踩了一次这个坑。

### 13.8 删掉 pointOfLineSide

修完 `revolveRay` 后，`checkPointLineSide` 的生产调用方清零（只剩 demo 脚本
`testJadeUtils.ts` 的 8 处），而 `pointOfLineSide` 本来就零调用 ——
只剩 `checkPointLineSide` 的 JSDoc 里一条 `{@link}` 引用它作对比说明。

两者的处理不同：

| 函数 | 处置 | 理由 |
|------|------|------|
| `pointOfLineSide` | **删** | 零调用。它就是展开写的标准叉积，需要时一行就能写出来，不值得作为公开 API 维护 |
| `checkPointLineSide` | **留** | demo 页面在用；而且它的方向归一化语义（对点序不敏感）不是一行叉积能直接替代的 |

删除后的处理：

- `checkPointLineSide` 的 JSDoc 改为与「裸叉积」对比，不再 `{@link}` 已删的函数
- 测试里专测 `pointOfLineSide` 的 describe 块删掉（2 条）——
  它验证的「两侧符号相反」「线上返回 0」已被 `checkPointLineSide` 的测试覆盖
- 另外 3 条用它演示叉积性质的测试改用 `checkPointLineSide`。
  后者的方向归一化只翻符号、不改绝对值，所以 `|cross|` 相关的断言照样成立
- 「等于裸叉积的相反数」那条改为内联算叉积，不再依赖被删的函数
- `geo.md`、`CLAUDE.md` 里的对比说明改写为「与裸叉积的区别」

实测确认过「绝对值不受方向归一化影响」这个前提：同一批输入下
`|checkPointLineSide|` 与 `|cross|` 完全相等，所以改用后断言等价。

### 14.2 jsdom 的装配方式

新增 `test/_jsdom-setup.ts`，提供 `withDom(html, fn)`：

```typescript
withDom('<div id="a"></div>', () => {
	// 这里 document / location / customElements 都可用
});
```

每次调用新建一个 JSDOM，退出时还原全部被覆盖的全局。所以**用例之间不会通过
document 或 cookie 互相影响** —— 这一点专门写了用例验证。

踩到一个坑：**Node 21+ 自带只读的 `navigator`**（只有 getter），
直接 `globalThis.navigator = ...` 会抛
`Cannot set property navigator of #<Object> which has only a getter`。
改用 `Object.defineProperty` 装配，并保存原始的属性描述符用于还原。

`test/*.test.js` 之外的文件不会被 `node --test` 当测试跑，
所以这个 helper 命名为 `_jsdom-setup.ts`（下划线前缀）放在同一目录即可。

### 15.2 `renderTopNav` 的模板注入

原来 `renderTopNav` 的第一行就是一整段 Bootstrap 3 骨架：`navbar-header`、
`navbar-toggle`、三个 `icon-bar`、`navbar-collapse`，子菜单用 `dropdown` +
`caret`。库层因此硬绑定 BS3 —— 用别的框架的人拿到的是一段带 BS3 class 的 HTML。

改成模板可注入：

```typescript
// 库：只定义类型 + 一个框架无关的默认实现
export type TopNavRenderer = (ctx: TopNavContext) => string;

renderTopNav(site: SiteConfig, elemSlt: string = "#topnav",
	render: TopNavRenderer = WebHtmlPage.renderPlainTopNav): void
```

`TopNavContext` 是渲染需要的全部输入（`items` / `brandName` / `brandLink` /
`activeTitle`），所以模板函数是纯函数 —— 不碰 DOM、不读实例状态，测试直接比字符串。
`activeTitle` 取自 `PageConfig.pageTitle`，用来标出当前页；原来这段是直接在渲染
过程里读 `this.cfg.pageTitle` 的。

两套模板的分工：

| 模板 | 位置 | 产出 |
|------|------|------|
| `WebHtmlPage.renderPlainTopNav` | 库层，默认值 | `a.nav-brand` + `ul.nav-list`，子菜单是 `ul.nav-sub`。零框架 class |
| `BootStrapHelper.renderTopNav` | `3rdLibTool.ts` | 原来那段 BS3 骨架，一字没改 |

BS3 的那份放进 `BootStrapHelper` 是因为它已经是本项目的 Bootstrap 适配层
（`initPhotoFrame()` 里也有一段 BS3 的模态框 HTML）。按 [3.4 节](#34-哪些不该发包)，
`3rdLibTool` 本来就不发包，BS3 的骨架留在那里不会污染库。

页面侧显式选框架：

```typescript
page.renderTopNav(site, "#topnav", BootStrapHelper.renderTopNav);
```

`blog/common.ts`、`blog/wiki.ts`、`testJadeUtils.ts` 三处调用都这样传 ——

### 16.1 资源注册表：310 行 base64 变成 opt-in

**问题不只是体积，还有「换不掉」。** 原来 `UIWindow.ts` 第 3 行就是
`import { JadeUIResource, ... } from "../resource.js"`，于是：

- 只想用窗口管理器的人也得下载 27.8 KB base64
- 想换图标只能改库的源码 —— `WinCfg.icons` 虽然可以逐个窗口传，

[ui/uiResource.ts](../src/scripts/ts/ui/uiResource.ts)（库层，零图片数据）：

```typescript
export interface IUIResourceProvider {

	getIconGroup(name?: string): IconGroup | undefined;
	getDesktopBackground(): IBase64Img | undefined;
}
export function registerUIResourceProvider(p: IUIResourceProvider | undefined): void;
export function getIconGroup(name?: string): IconGroup | undefined;
export function getDesktopBackground(): IBase64Img | undefined;
```

|------|------|-----------|

| `ui/UIWindow.ts` | 消费方，只认注册表 | 否 |
| `resource.ts` | 内置资源 + `registerDefaultUIResource()` | 是，310 行 |

**没注册时返回 `undefined`，不兜底成任何内置图片** —— 这是整件事的关键。
兜底成某张图就等于没拆，所以 `uiresource.test.ts` 里专门有三条用例盯这个。
对应地 `WinCfg.icons` 从必填改成可选，两处渲染点加了判空：

| 渲染点 | 没图标时 |
|--------|---------|
| 标题栏图标（12px） | 加 `.no-icon` class，CSS 把宽度和右边距收掉，标题文字不会凭空缩进 |
| dock 任务项（32px） | 加 `.no-icon` class，CSS 画一个 98 风格的空方块，否则点不到 |

改成**取不到就一行都不写**。写空串会盖掉样式表里的值，比不写更糟。

### 16.3 vimwiki 路径从库层挪到应用层

**这一项原来标的卡点估错了。** 0.1 节写的是「外部依赖：`initWikiPage()` 的调用方

同类的教训在 [10.1 节](#101-问题是怎么暴露的)有过一次：
当时也是先假定了一个阻塞，后来发现问题性质不是那样。
标卡点的时候要分清「真的要等别人」和「我还没想清楚怎么做」。

## 17. src/themes 的目录重组

实施日期：2026-11-02。这一项不在 0.1 节的优先级表里 —— 它是[阶段 3](#阶段-3主题模块化动-less)
（主题模块化）的前置步骤，顺手先做掉。

### 17.1 问题：目录没反映依赖关系

原来 `src/themes/` 下是平铺的：

```
src/themes/
├── comm.less          ← 只服务于下面三个，但看不出来
├── hobbit/
├── lo-fi/
├── paper-print/
├── window-ui/         ← 压根不碰 comm.less
├── trpg/              ← 同上，而且没有 styles/
└── workout/           ← 同上
```

`comm.less` 和六个目录平级，看不出它只给三套内容主题用。而
`window-ui` / `trpg` / `workout` 各自是独立的一套，和那三个混在一层。

改成按「属于哪个应用」分组：

```
src/themes/
├── blog/              ← comm.less + 三套内容主题
│   ├── comm.less
│   ├── hobbit/
│   ├── lo-fi/
│   └── paper-print/
├── window-ui/
├── trpg/
└── workout/
```

**产物同构**：`webroot/themes/blog/<theme>/`，页面引用也跟着带 `blog/`。
源码和产物保持一致，不用在脑子里维护两套映射。

### 17.2 为什么 CSS 一个字都不用改

`part.1.less` 里有 56 处 `url()`，全是 `../images/xxx` 这种形式。
**它们相对的是产物 CSS 自己的位置，不是源码位置**：

```
webroot/themes/blog/hobbit/styles/all.css   里的 url(../images/bg.jpg)
→ webroot/themes/blog/hobbit/images/bg.jpg  ✅
```

`styles/` 和 `images/` 的相对关系在搬动前后没变，所以 CSS 内容不需要动。
这也是为什么能用「产物逐字节一致」来验证 —— 见 17.5 节。

另外全项目 **0 条 `@import`**，没有跨文件的路径依赖要跟着改。

### 17.3 改了哪些地方

| 文件 | 改动 |
|------|------|
| `src/themes/` | `git mv` 搬 4 个路径，103 个文件被 git 识别为 rename（历史保住） |
| `gulpfile.js` | 5 处路径常量，抽出 `blogThemeRoot = 'themes/blog/'` 统一 |
| `src/html/` | 13 处引用：`head.html` 4、`test-jade-wiki.html` 5、`test-jade-blog.html` 2、`test-jade-cdn.html` 2 |

**不用改的**：

- `build.sh` / `upload.sh` —— 是 `cp -r webroot/*` 和 `scp -r src`，不枚举主题名
- `changeTheme()` —— 匹配的是 `lnk.title == themeName`，cookie 存的也是 `hobbit`
  这种名字，**与路径无关**
- `window-ui` / `workout` / `trpg` 的 14 处页面引用 —— 这三套深度没变
- TypeScript 源码 —— 没有任何地方写死主题产物路径（路径都走 `@@staticRoot`）

### 17.4 两个踩过的点

**一、`paper-print` 的路径在 `head.html` 里出现两次。**
它外面套了一层 processhtml 的构建注释：

```html
<!-- build:[href] @@staticRoot/themes/blog/paper-print/styles/all.min.css?v=@@buildversion -->
<link title="paper-print" ... href="@@staticRoot/themes/blog/paper-print/styles/all.css?v=@@buildversion" />
<!-- /build -->
```

注释里是 rls 用的（`all.min.css`），`link` 上是 dev 用的（`all.css`）。
**只改一处会让 dev 和 rls 指向不同位置**，而且 dev 构建不会报错 ——
`process-html-rls` 跑起来才看得出。所以验证里专门跑了一遍 rls。

**二、glob 合并的陷阱。** 新结构下「把两个 glob 合成一个」很有诱惑力，
因为 blog 相关的全在一个目录下了。但那样是坏的，实测：

| 写法 | concat 顺序 |
|------|------------|
| `['blog/hobbit/styles/**/*.less', 'blog/comm.less']` | part.1 → shCore → shTheme → **comm.less** ✅ |
| `['blog/**/*.less']` | **comm.less** → hobbit/… → lo-fi/… → paper-print/… ❌ |

`blog/comm.less` 的字典序排在 `blog/hobbit/` 前面，合并之后 concat 顺序反掉
（Less 变量最后赋值生效，顺序一反主题色全失效），而且三套主题会被合进同一个文件。

好消息是另一个更危险的失败模式会自己叫出来：实测 `comm.less` 路径写错时

### 18.1 提出的切分

| 公用 TypeScript 库 | web 项目 |
|-------------------|---------|
| `src/themes/window-ui/` | `src/html/` 下所有 HTML |
| `src/scripts/ts/ui/`（6 个文件） | `src/themes/blog/`、`trpg/`、`workout/` |

包边界少一个数量级，不用维护 8 份 `package.json` 和 8 条版本线，
TS project references 只有一条边。代价是库的使用方拿不到「只装几何库」这种粒度。

### 18.2 核对方法

把两份清单当成文件前缀规则跑了一遍全量依赖分析（脚本逻辑见 18.8），
查三件事：有没有文件没被覆盖、有没有「库 → web」的反向依赖、依赖方向是否单向。

结果：

| 项 | 结果 |
|----|------|
| 25 个 `.ts` 文件的覆盖 | **漏 1 个**：`env.demo.ts` |
| web → 库（正常方向） | 24 条，都合规 |
| 库 → web（反向，不允许） | **6 条，全部来自 `index.ts`** |

### 18.3 硬阻塞：`index.ts` 的 6 条反向依赖（已定案：B 方案）

`index.ts` 是 `export *` 汇总入口，它 re-export 了 web 侧的 6 个模块：

```
index.ts → trpg/sandtable.ts
         → blog/blog.ts
         → blog/wiki.ts
         → workout/workout.ts
         → workout/workoutData.ts
         → workout/workoutPoseData.ts
```

**这是整个切分里唯一的硬阻塞** —— 库不能依赖 web 项目，否则两边编译不开。

三种解法：

| 解法 | 做什么 | 代价 |
|------|--------|------|
| A. 库的 `index.ts` 只汇总库模块 | 删掉那 6 行 `export *` | 不带子路径的 `import ... from '@jade-dungeon/jade-utils'` 拿不到 blog/workout/sandtable 了，是 breaking change |
| B. 两边各有一个汇总入口 | 库留 `index.ts`，web 项目加自己的 | web 侧的汇总入口没有发布意义（web 项目不发包），等于白加一个文件 |
| C. 干脆删掉 `index.ts` | 全部改用子路径导入 | README 已经在推荐子路径导入（「没有打包器做 tree-shaking」），这条反而是顺水推舟 |

~~倾向 A~~ —— **定案：B 方案**（2026-11-02）。两边各有一个汇总入口，结构对称。

注意 **B 在实现上包含 A 对库的全部改动** —— 库的 `index.ts` 同样要删那 6 行，
否则反向依赖还在、两边编译不开。差别只是 web 侧多一个汇总入口文件。
这一点容易误解，详见 [18.12-(1)](#1812-已确认的切分决定与连带后果)。

按 [8.2 节](#82-breaking-change-要攒在一起发)，这条 breaking change
和已累积的那批一起发 4.0.0。

### 18.4 漏项：`env.demo.ts`（已定案：各留一份）

两份清单都没提到它。它是 demo 页面的环境配置（`apiRoot` / `themeRoot` / `cdn3rd`），
被两边同时使用：

```
testJadeUtils.ts      [库]  → env.demo.ts
trpg/testJadeTRPG.ts  [web] → env.demo.ts
```

所以它既不能只放库、也不能只放 web。两种处理：

- **各留一份**：两边都是 demo 专用、都不发布，复制一份 41 行的文件不算重复代码灾难，
  而且将来两边的 demo 环境需求可能分叉
- **放库、web 侧 import**：少一份文件，但库要为「demo 环境」这个纯应用概念留一个导出

**定案：各留一份**（2026-11-02）。它本来就不在 `exports` 里（[第 11 节](#11-demo-环境配置注入与跨源判定修正)
刻意这么定的），复制比让库背一个应用概念干净。

### 18.5 四处归属值得商量（已全部定案）

四条的结论：(1) 采纳、(2) 不采纳（归 web）、(3) 采纳「拆两半」、(4) 不采纳（留库）。
下面保留当时的论证。

#### (1) `site.config.ts` 应该在 web 侧，不在库

清单把它放在库里。但这个文件是**本站配置** —— 品牌名 `Jade Dungeon`、
导航树、个人 GitHub 链接。[15.1 节](#151-site_nav_items--site_themes-挪出库层)
刚把这些值从库层（`ui/webHtmlPage.ts`）清出去，理由就是「库不该带某一个站点的信息」。
放回库里等于把 P1 做的事撤销一半。

事实支持这个判断 —— 它的 4 个使用方全在 web 侧：

```
blog/blog.ts、blog/common.ts、blog/gallery.ts、blog/wiki.ts
```

库里只有 `ui/webHtmlPage.ts` 的一行注释提到它，不是代码依赖。

**结论：挪到 web 侧。** 库留 `SiteConfig` 类型（已经是这样了）。

#### (2) `trpg/sandtable.ts` 可能该在库侧，不在 web

清单把它放在 web 侧。但它看着更像库：

| 指标 | 情况 |
|------|------|
| 规模 | 672 行 |
| 依赖 | 只依赖 `basic` / `ui/canvas` / `ui/geo2d` / `web` —— 全是库模块 |
| 业务假设 | 无。Token 管理、视野计算、战争迷雾都是通用的战棋逻辑 |
| 本站耦合 | 无写死地址（写死的生产 URL 在 `testJadeTRPG.ts` 的 `testSceneData` 里，那是 demo） |
| 3.3 节的定位 | 列为可发布包之一，理由「超过 600 行、功能自成体系」 |

它在 web 侧的唯一使用方是 `trpg/testJadeTRPG.ts`（demo）。

**但有个反方理由**：沙盘是给这个站点的 TRPG 页面做的，短期内不会有别的使用方。
放库里要承担「对外公开 API」的约束（改签名就是 breaking change），而放 web 侧可以随便改。

**定案：归 web 侧**（2026-11-02），采纳的就是这条反方理由 ——
短期内没有别的使用方，不值得为它承担 API 稳定性约束。
这意味着放弃 [3.3 节](#33-包边界的取舍)把它列为可发布包的定位。
将来真有别的使用方时再挪回库侧，那时它的 API 也沉淀得更稳了。

#### (3) `3rdLibTool.ts` 放库里有矛盾

清单把它放库里，但 [3.4 节](#34-哪些不该发包)明确写了它**不该发包**：
它包装的是 `$` / `MathJax` / `SyntaxHighlighter` / `showdown` 四个**全局变量**，
npm 消费方装的是真包（`import $ from 'jquery'`），这层包装会错位。

同时它又不能放 web 侧 —— [15.2 节](#152-rendertopnav-的模板注入)把 BS3 的导航栏骨架
挪进了 `BootStrapHelper.renderTopNav`，而 `ui/webHtmlPage.ts` 的
`TopNavRenderer` 类型是给它用的。使用方分布：

```
index.ts、testJadeUtils.ts  [库]
blog/common.ts、blog/wiki.ts [web]
```

两边都用。三种处理：

| 处理 | 说明 |
|------|------|
| 放库但标记 `private`/不导出 | 库内部可用，不进 `exports`，web 侧通过相对路径或 workspace 依赖引用 |
| 放库并照常导出 | 和 3.4 节的判断冲突，但省事；可以在 README 写明「这个子路径不建议 npm 消费方用」 |
| 拆两半 | 纯模板函数（`renderTopNav`）进库，依赖全局变量的部分（jQuery/MathJax 封装）进 web |

~~倾向第一种~~ —— **定案：第三种，拆两半**（2026-11-02）。纯模板函数进库，
依赖全局变量的部分进 web。这是三种里最彻底的 —— 库里不再有任何依赖全局脚本的代码，
3.4 节「不该发包」的判断也就不再适用于库侧那部分。

**但拆的位置不在类的边界上**，`BootStrapHelper` 这个类本身要被切开，
而且有一个方法会被误分。详见 [18.12-(2)](#1812-已确认的切分决定与连带后果)。

#### (4) `src/themes/window-ui/images/favicon.ico` 该在 web 侧

清单把整个 `src/themes/window-ui/` 放库里。styles 部分（`desktop.less`）确实是库的 ——
它和 `ui/UIWindow.ts` 配套。但那个目录里还有一个 `favicon.ico`，
**被 10 个页面引用**，其中包括 web 项目的 `index.html` 和所有页面共用的 `parts/head.html`。

这是 [17.6 节](#176-刻意没改的)记下的「分组和事实不吻合」那条。当时建议趁切 workspaces 处理：

```
src/themes/window-ui/styles/desktop.less  → 库（和 UIWindow.ts 配套）
src/themes/window-ui/images/favicon.ico   → web 项目（站点级资源）
```

**定案：采纳，`favicon.ico` 归 web 侧**（2026-11-02 确认，当日修正）。
库的 `src/themes/window-ui/` 只保留 `styles/desktop.less`。

> 这一条先定成「留库侧」，当天修正为「归 web 侧」。
> 修正的理由就是本小节原本的论证：favicon 是**站点级资源**，
> 和窗口 UI 没有关系，放 `window-ui/` 下纯属历史沿革。
> 库是纯 TypeScript 库 + 窗口 UI 样式，不该附带站点的品牌资源。

这同时解决了 [17.6 节](#176-刻意没改的)记下的那个语义问题 ——
不用留到阶段 4 了。落地细节见 [18.12-(3)](#1812-已确认的切分决定与连带后果)。

### 18.6 一个结构性矛盾：demo 页面（已定案：全归 web）

「`src/html/` 下所有 HTML → web 项目」这条规则和「`testJadeUtils.ts` → 库」冲突。
实际的驱动关系：

| `test-jade-window-ui.html` | `ui/testJadeUI.ts` | 库 |

| `test-jade-cdn.html` | `testJadeUtils.ts` | 库 |
| `test-jade-blog.html` | `testJadeUtils.ts` | 库 |

| `test-workout.html` | `workout/testWorkout.ts` | web |
| `test-jade-trpg-ui.html` | `trpg/testJadeTRPG.ts` | web |
| `test-jade-trpg-compose.html` | `trpg/testJadeTRPG.ts` | web |

**5 个 demo 页面的驱动脚本在库侧。** 注意 `test-jade-blog.html` 和
`test-jade-wiki.html` 名字带 blog/wiki，但驱动脚本是库的 `testJadeUtils.ts`，
不是 `blog/` 下的代码 —— 按名字分会分错。

两种处理：

- **demo 页面跟着脚本走**：库带自己的 5 个 demo 页面，web 项目带 3 个。
  代价是 `src/html/parts/` 的 5 个片段两边都要用（`head.html` 含 import map），

**定案：第二种，且库的 demo 脚本也归 web**（2026-11-02）—— 即
`testJadeUtils.ts` 和 `ui/testJadeUI.ts` 都在 web 项目。理由：
它们是**验证手段**而不是库的组成部分，`tsconfig.build.json` 本来就把 `test*.ts`
排除在 npm 包之外。库的自动化验证靠 `test/` 下的 230 个用例，不靠这两个脚本。

结果是**库变成纯 TypeScript 库：零 HTML、零 `test*.ts`**。
连带两处影响见 [18.12-(4)](#1812-已确认的切分决定与连带后果)。

### 18.9 切分之后要改的构建

两份清单都没覆盖构建侧，但这部分工作量不小：

**`buildImportMap()` 这一条被决定 11 简化了很多。** 包名和 20 个子路径全不动，
所以映射表产出的 JSON **一条都不会变** —— 只是 `fs.readFileSync('./package.json')`
要改成读 `lib/package.json`。[9.6 节](#96-阶段-2-拆包时要做的事)说的「遍历
`packages/*/package.json`，十几行的改动」在这个切法下连遍历都不需要。

#### `gulpfile.js` 和 `build.sh` 的拆法（已定案：各一份）

当时考虑过三种：

| 做法 | 说明 |
|------|------|
| **各一份**（`lib/gulpfile.js` + `web/gulpfile.js`） | 边界最清楚，每份只管自己的任务。代价是 TS 编译那段逻辑两边都要有，会有重复 |
| 根上一份，用参数区分（`npx gulp build --target=lib`） | 不重复，但一份文件里混着两边的路径常量，容易改错 |
| 根上一份 + 各自一份薄壳 | 公共逻辑抽到根上的共享模块，两边各写只有路径常量的 gulpfile |

**定案：各一份**（决定 15 / 16）。第三种听起来最干净，但本项目的 gulpfile 现在是
**任务定义式**的（`gulp.task(...)` 直接注册、路径常量内联在任务里），
抽公共逻辑要先把它重构成函数式，那是一次独立的重构 ——
和切 workspaces 混在一起做会让 diff 难读、出错难定位。

**接受的重复**：两边都要有一段编译 TS 的任务。实际重复量不大 ——
`process-typescript` / `compress-typescript` 两个任务的主体是
`ts.createProject(...)` + uglify，各自指向不同的 tsconfig 和输出目录。

拆分后各自管什么：

| | `lib/gulpfile.js` | `web/gulpfile.js` |
|---|------------------|-------------------|
| TS 编译 + 压缩 | ✅ | ✅ |
| window-ui 主题（Less） | ✅ | — |
| blog 三套主题（Less + comm.less concat） | — | ✅ |
| workout 主题（Less） | — | ✅ |
| trpg / site 图片拷贝 | — | ✅ |
| HTML 模板展开（fileinclude / processhtml） | — | ✅ |
| `buildImportMap()` | — | ✅（读 `lib/package.json`） |

注意最后一条：**`buildImportMap()` 归 web 侧**，但它读的是**库的**
`package.json`（决定 11 让子路径全不动，所以内容一条不变）。
import map 是给页面用的，而页面全在 web 侧。

**第三种做法留作将来的选项** —— 如果以后 gulpfile 被重构成函数式的，
或者库再细分成多个包导致重复变多，可以再改。现在不值得。

四条连带后果，其中两条是决定本身蕴含但没明说的：

#### (1) 决定 2 必然包含「删库的 `index.ts` 那 6 行」

「两边各有一个汇总入口」看起来像是「库的 `index.ts` 不动，web 侧加一个」，
但实测跑分配之后，**那 6 条反向依赖仍然存在**：

```
index.ts → trpg/sandtable.ts、blog/blog.ts、blog/wiki.ts、
           workout/workout.ts、workout/workoutData.ts、workout/workoutPoseData.ts
```

库的 `index.ts` 只要还 `export *` 这 6 个模块，库就还依赖 web 项目，两边编译不开。
所以 **B 方案在实现上等于「库的 `index.ts` 删 6 行 + web 侧新建一个汇总 6 个模块的
`index.ts`」**，和 A 方案对库的改动完全相同，差别只是 web 侧多一个文件。

这条不是反对 B 方案 —— 结构对称有它的价值。只是记清楚：**B 不等于「库不用改」**。

#### (2) 决定 6 的拆法会切开 `BootStrapHelper` 这个类

逐方法查了依赖（结果如下），「纯模板 / 依赖全局」这条线**不沿类的边界走**：

| 类 | 方法 | 依赖的全局变量 |
|----|------|--------------|
| `SyntaxHighlighterHelper` | `loadCodeHightlight` | `SyntaxHighlighter` |
| `MathJaxHelper` | `defaultMathJaxCfg` / `defaultQueue` / `initMathJax` | `MathJax` |
| **`BootStrapHelper`** | **`renderTopNav`** | **无** |
| **`BootStrapHelper`** | **`initPhotoFrame`** | **无** |
| `BootStrapHelper` | `viewPic` | `$` |
| `BootStrapHelper` | `bindImageFrame` | **间接** —— 点击回调里调 `viewPic` |
| `DataTableHelper` | `bindInitDataTable` | `$` |
| `ShowdownUtils` | `makeHtml` | `showdown` |

三个类可以整个归 web（`SyntaxHighlighterHelper` / `MathJaxHelper` / `DataTableHelper` /
`ShowdownUtils`），但 `BootStrapHelper` 的 4 个方法里有 2 个纯、2 个依赖 `$`。
**同名的类不能同时存在于两个包里**，所以要重新命名。建议：

```
库：  BootStrapTemplate.renderTopNav()      ← 纯字符串拼接，产出 BS3 骨架
      BootStrapTemplate.initPhotoFrame()    ← 纯 DOM，写 innerHTML
web： BootStrapHelper.viewPic()             ← 要 $ 的 modal
      BootStrapHelper.bindImageFrame()      ← 绑点击，回调里调 viewPic
```

注意 `bindImageFrame` 看着是纯 DOM（只有 `querySelectorAll` 和 `onclick`），
但它的点击回调里调 `BootStrapHelper.viewPic`，而那个要 jQuery 的 `.modal()`。
**按「有没有写 `$`」判断会把它误分到库侧**，运行时才会在用户点图片时炸。

好消息：`ui/webHtmlPage.ts` 里只有**注释**提到 `BootStrapHelper`（第 86、116 行），
没有代码依赖。所以库侧不会因为这个拆分产生新的跨包依赖。

#### `initPhotoFrame` 归哪边（已定案：归 web）

`initPhotoFrame` 是纯 DOM（只写 `innerHTML`，不碰全局变量），
按「纯的进库」应该归库。**但它和 `viewPic` 是一对**：

```
initPhotoFrame()  写出 #photo-frame-label 和 #photo-frame-img 两个 id
       ↓ 隐式契约（靠 id 字符串约定）
viewPic()         按这两个 id 找元素，然后调 $().modal()
```

分开放会让这个隐式契约跨包 —— 改 `initPhotoFrame` 的 id 命名就会悄悄弄坏
web 侧的 `viewPic`，而编译期查不出来。

两个选项：

| 做法 | 库侧有什么 | 代价 |
|------|-----------|------|
| **只有 `renderTopNav` 进库** | 1 个方法 | 最干净，`initPhotoFrame` / `viewPic` 这对留在一起 |
| `renderTopNav` + `initPhotoFrame` 进库 | 2 个方法 | 隐式契约跨包，要在两边都写注释说明 |

**定案：第一个**（决定 14）—— 库侧的 `BootStrapTemplate` 只有 `renderTopNav` 一个方法。
它是 [15.2 节](#152-rendertopnav-的模板注入)为了解除库对 BS3 的硬绑定才挪进来的，
那个理由只适用于 `renderTopNav`（它是 `TopNavRenderer` 的一个实现）；
`initPhotoFrame` 没有同类的「库需要它」的理由。

#### 拆分后的最终形态

```
lib/ui/bootstrapTemplate.ts        ← 新文件
      export class BootStrapTemplate {
          static renderTopNav(ctx: TopNavContext): string   // 纯字符串拼接
      }
      —— 库侧到此为止，零全局变量依赖

web/  3rdLibTool.ts（保留原文件名）
      SyntaxHighlighterHelper     全部（依赖 SyntaxHighlighter）
      MathJaxHelper              全部（依赖 MathJax）
      DataTableHelper            全部（依赖 $）
      ShowdownUtils              全部（依赖 showdown）
      BootStrapHelper            initPhotoFrame / viewPic / bindImageFrame
                                 （renderTopNav 挪走了）
```

**库侧从此没有任何依赖全局脚本的代码** —— [3.4 节](#34-哪些不该发包)
说 `3rdLibTool` 不该发包的理由（依赖 `$` / `MathJax` 等全局变量）
对库侧那一个方法不再适用。

改动会牵动三个文件的 import：

| 文件 | 原来 | 改成 |
|------|------|------|
| `web/blog/common.ts` | `BootStrapHelper.renderTopNav` | `BootStrapTemplate.renderTopNav`（从库 import） |
| `web/blog/wiki.ts` | 同上 | 同上 |
| `web/testJadeUtils.ts` | 同上 | 同上 |

这三处同时还在用 `BootStrapHelper.initPhotoFrame` / `bindImageFrame`，
所以改完之后它们会同时 import 两个来源 —— 一个来自库、一个来自 web 自己的

### 18.13 产物路径拆开之后的连带改动

决定 12 选了「两个独立的 `webroot/`」。这一条看着只是构建输出的事，
但**它会牵动 `envs.js` 的变量设计和 27 处 HTML 引用**，要先算清楚。

#### 问题：web 的页面引用库的产物

实测统计了 `@@staticRoot` 的全部用途（27 处）：

| 引用的东西 | 处数 | 产物属于 |
|-----------|------|---------|
| `themes/window-ui/images/favicon.ico` | 10 | **库** |
| `themes/window-ui/styles/all.min.css` | 3 | **库** |
| `themes/blog/<theme>/...` | 13 | web |
| `themes/workout/styles/...` | 1 | web |

（另有 2 处 `@@staticRoot/themes` 作为 `themeRoot` 传给 TRPG demo，指向 web 的 trpg 图片。）

favicon 那 10 处按决定 13 会挪到 web 的 `themes/site/`，所以不再跨界。
**但 `themes/window-ui/styles/all.min.css` 那 3 处是真跨界** ——
`test-jade-window-ui.html`（2 处）和 `test-jade-trpg-ui.html`（1 处）
是 web 项目的页面，引用的是库的窗口 UI 样式。

#### 解法：`staticRoot` 拆成两个

现在 `envs.js` 只有一个 `staticRoot`，注释写的是「静态资源（主题 CSS、图片、favicon）
的根路径」。两个 webroot 之后一个值不够用：

```javascript
// envs.js（dev 段）
libRoot:    "http://.../jadeutils.v3-lib",   // 库的产物根：themes/window-ui/
staticRoot: "http://.../jadeutils.v3",       // web 的产物根：themes/blog|trpg|workout|site/
importMapRoot: "<libRoot>/scripts/ts",       // 模块路径基址，指向库
```

对应 HTML 的改动：

| 引用 | 改成 |
|------|------|
| `@@staticRoot/themes/window-ui/styles/all.min.css` | `@@libRoot/themes/window-ui/styles/all.min.css` |
| `@@staticRoot/themes/window-ui/images/favicon.ico` | `@@staticRoot/themes/site/images/favicon.ico` |
| 其余 `@@staticRoot/themes/...` | 不变 |

**`importMapRoot` 现在在语义上属于库** —— 它指向库的 `scripts/ts/`。
两个 webroot 之后它要跟着 `libRoot` 走，不能再和 web 的 `staticRoot` 同源。

#### 代价：验证手段变弱了

这是选两个 webroot 最实际的代价。第 17 节用的「**产物逐字节一致**」
那条最强的回归检查，在这里**不再直接可用** ——
产物分到两个目录树之后，没法简单地和切分前的单个 `webroot/` 做整树比对。

补救办法是分别比对：

```
lib/webroot/scripts/ts/      ↔ 旧 webroot/scripts/ts/
lib/webroot/themes/window-ui/ ↔ 旧 webroot/themes/window-ui/
web/webroot/html/            ↔ 旧 webroot/html/     （favicon 和 window-ui 的 href 会不同）
web/webroot/themes/blog/     ↔ 旧 webroot/themes/blog/
```

前两组和后一组的 `themes/` 应该逐字节一致（内容没动），
只有 `html/` 因为 13 处 `href` 改了而必然不同 —— 那部分改用
「每个 `href` 都能解析到真实文件」来验证（第 17 节已经有这个脚本）。

#### 如果想保住强验证

合并到同一个 `webroot/` 的话（当时的另一个选项），`staticRoot` 不用拆、
HTML 只需要改 favicon 那 10 处、整树逐字节比对直接可用。
**现在选了拆开，所以上面那套分组比对是必须做的** ——
记在这里是为了实施时不漏掉。

#### 部署侧

两个 `webroot/` 最终怎么合到 CDN 上，有两种做法：

- **分开部署**：CDN 上两个路径（如 `jadeutils.v3-lib/` 和 `jadeutils.v3/`），
  `envs.js` 的两个 root 分别指向。边界最清楚，但要配两处 nginx
- **部署时合并**：`cp -r lib/webroot/* web/webroot/* → 同一个目标`，
  两个 root 填同一个值。构建期分开、部署期合并，`envs.js` 退化成和现在一样

第二种更省事，而且**保留了随时切换的余地** —— 两个 root 是独立变量，
填同一个值就是合并，填不同值就是分开。建议先按第二种部署，
`envs.js` 里两个变量都留着。
